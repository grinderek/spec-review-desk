# Desk: Event Sourcing и самостоятельные исполняемые спецификации

## Зачем

Desk уже исполняет YAML-контракты и восстанавливает согласования из событий. Однако обсуждения,
решения владельца, планы и состояние запусков остаются изменяемыми YAML-документами. События
согласований вычисляются из разницы документов. Бизнес-правила распределены между HTTP routes,
сервисами и функциями хранения. Внутренний процесс зависит от структуры и CLI OpenSpec, а
названия сценариев дублируются в Markdown.

Цель, выбранная владельцем 19.10.2026: перевести бизнес-логику Desk на Event Sourcing, затем
убрать внутреннюю зависимость от OpenSpec. Исполняемые спецификации остаются договором о
поведении; реализацию за этим договором можно заменять поэтапно.

## Что предлагаем

1. Выделить команды, события и восстановление состояния на существующем потоке согласований.
2. Переносить связанные продуктовые процессы вертикальными срезами: обсуждения и решения,
   инициативы и research, исполнение и восстановление после прерывания.
3. Сделать YAML-представления производными для уже перенесенных областей. Источником текущих
   текстов контрактов и файлов продукта остаются рабочее дерево и Git.
4. Выполнять спецификации через публичные операции: prior events + environment, одна команда,
   новые события и публичные ответы. Сохранить компактность языка и читаемость для владельца.
5. Ввести собственный пакет изменения Desk, получая документацию из исполняемых контрактов.
   OpenSpec оставить адаптером совместимости для существующих и внешних проектов.

Это план миграции, а не начало переписывания приложения. Детали, зависимости, критерии выхода
и ограничения отката описаны в [design.md](design.md), очередь работ - в [tasks.md](tasks.md).
Разбор восьми глав и соответствия текущему коду - в [research.md](research.md).
Дополнительная проверка обоих видео и доступных исходников - в [video-code-review.md](video-code-review.md).

## Границы

- Сохраняем семантику hash-bound approvals. По уточнению владельца внутренняя backward
  compatibility не нужна: S1 читает один целевой формат, без импортов старых snapshots.
  Историю владельца агент не правит; неподдерживаемый формат явно отвергается.
- Не добавляем техническую тестовую коллекцию. Используем существующие контракты, браузерные
  проверки, typecheck и ручную проверку конкретного среза по AGENTS.md.
- Текущие правила AGENTS.md о YAML-хранении остальных областей действуют до отдельного
  согласования соответствующего среза. Этот план сам по себе их не изменяет.
- Не меняем сейчас React UI, HTTP API, рабочие конфигурации, изоляцию агентов и модель доступа.
  Kafka, брокер сообщений и отдельная серверная БД для этой миграции не требуются.
- Преимущества ES в скорости и стоимости не считаем доказанными без измерений на Desk.

## Статус

S1 реализован в [approval-command-events](../approval-command-events/proposal.md), включая
первый approve/revoke срез. Согласование через Desk агентом не записывалось. S2-S7 не начаты.
Совместимость внешних OpenSpec-проектов в S6-S7 рассматривается отдельно; она не требует
поддержки старых внутренних approval форматов в S1.

В этом пакете пока нет новых `features/` и `specs/`: он задает последовательность технической
замены, а не вводит новое продуктовое правило. Для каждого поведенческого изменения сначала
готовится отдельный behavior-driven change с компактными контрактами под `features/`, стабильными
id и соответствующими заголовками `specs/**/spec.md`. Утвержденный corpus не переписывается ради
прохождения новой реализации.
