# Поэтапная замена реализации Desk

## Результат

Для бизнес-состояния перенесенных областей действует цепочка:

```text
HTTP / внешний результат
  -> application command
  -> история + текущие входные факты + проверка версии
  -> решение предметной области
  -> новые события
  -> атомарная запись одной группы событий
  -> проекции / публичный ответ
  -> уведомления и устойчиво запланированные внешние действия
```

История объясняет принятые решения. Представления восстанавливаются. Спецификации описывают
один публичный стимул и наблюдаемые последствия. Пакет изменения Desk не требует CLI OpenSpec
и ручной копии сценариев в Markdown.

## Границы модели

Начинаем с двух границ согласованности, а не с отдельного агрегата на каждый файл:

| Поток | Состояние и правила | Возможные команды и факты |
| --- | --- | --- |
| Review scope одного change | Approvals, обсуждения, решения владельца, допуск и жизненный цикл Apply. Эти данные вместе определяют возможность реализации. | `ApproveScenario`, `RequestScenarioChanges`, `ResolveDiscussion`, `ChooseOwnerDecision`, `RequestApply`; существующие approval events, затем `DiscussionResolved`, `OwnerDecisionChosen`, `ApplyRequested`. |
| Initiative scope | Brief/input references, черновик и согласование плана, зависимости slices, решения владельца, разрешения research, жизненный цикл research/planner/author. | `ApprovePlan`, `AcceptResearchInput`, `GrantResearchReading`, `ProposeSlice`; `PlanApproved`, `ResearchInputAccepted`, `ResearchReadingGranted`, `SliceProposalRequested`. |

Названия новых событий - рабочие предложения. Финальная модель уточняется по реальным
переходам и вопросам владельца. Discussions, Decisions и Execution могут стать отдельными
модулями кода, оставаясь частью потока соответствующего scope. Отдельный поток запуска имеет
смысл выделять позже, только если он сохраняет необходимые атомарные gates.

Выбор двух scope - наша начальная гипотеза для Desk. Перед S1 раскладываем один процесс
согласования по цепочке actor -> view -> command -> event -> следующий view. Спорные правила
отмечаем отдельно; границы уточняем после этой карты. Карта важнее соответствия существующим
файлам и не означает обязательного создания Event Storming UI внутри продукта.

Процесс между initiative и authored change координируется application workflow с устойчивой
корреляцией и идемпотентной регистрацией результата. Не предполагаем атомарную транзакцию
между двумя потоками, Git и файловой системой.

Тексты контрактов, исходники продукта, Git HEAD и загруженные файлы не заменяются журналом
Desk. Их версии и content hashes являются входными фактами команд. Readiness - результат
истории review плюс текущих контрактов, decisions, threads и corpus. Проекция не имеет права
сама выдать разрешение на Apply. Команда проверяет условия заново.

## События и хранение

Уточнение владельца от 19.10.2026: внутренняя обратная совместимость Desk не требуется.
Для S1 действует один целевой approval journal format, описанный в
[approval-command-events](../approval-command-events/design.md). Это заменяет прежний план
legacy decoder, import checkpoints и временного snapshot diff bridge.

- Все approval-команды явно решают события из replayed state и текущих входных фактов.
- Поддерживается только envelope version 2: stream/event/command UUIDs, sequence с 1,
  timestamp, origin `approval-command` или `fixture`. История v1 и checkpoints отвергаются.
- Approval YAML без поддерживаемого журнала явно отклоняется. Импорта и автоматического
  преобразования неизвестных workspaces нет. Настоящую историю владельца агент не редактирует.
- Файловый storage сохраняет целую группу событий с byte-version CAS и atomic rename.
  Логическая неизменяемость важнее оптимизации append; стоимость записи растет с историей.
- Один serialized writer на review scope: canonical path queue и advisory flock WSL/Linux.
  Независимые changes могут записываться одновременно. Лок не защищает от внешних редакторов,
  Git-команд и writers с отдельным temp directory. CAS не заменяет участие writer в протоколе.
- Первый event устанавливает UUID потока. Это не UI worktree id. Потоки разных ветвей не
  сливаются автоматически. Обновление формата в будущем требует отдельного решения.
- Approval projection восстанавливается из журнала. Discussions, decisions и runs остаются
  авторитетным mixed YAML до отдельных S2-S4. Поврежденный YAML не считается пустым.
- Initial request-changes thread записан в событии, но добавляется в YAML только новой командой.
  Replay не заменяет последующее обсуждение начальным thread; восстановление discussions - S2.

Не нужен дополнительный глобальный domain log: вначале проекции workspace строятся по
согласованным позициям потоков. Между независимыми потоками не обещаем полного временного
порядка. Общий feed можно добавить позже с явной моделью порядка и доставки.

## Эффекты и восстановление

Replay только восстанавливает состояние. Он не запускает Codex, Docker, browser, Git commit
или запись решения во внешний журнал. Уведомления UI отделены от доменных событий.

В учебном примере агрегат обращается к IServiceGuy непосредственно. Для Desk отделение
долгих внешних действий - наше проектное решение: decision/replay получает уже зафиксированные
входные факты, а CLI и Git обслуживаются application workflow. Новый взгляд из старой истории
получает только сведения, действительно присутствующие в событиях и доступных версиях файлов.

Для длительного действия сохраняем intent и execution id, затем исполняем его и сохраняем
результат. Не обещаем exactly-once для внешнего CLI. При сбое между запуском и записью результата
Desk проверяет уже существующий process/container/log/commit по execution id. Если факт
выполнения не удается установить, показывает неопределенность и требует явного resume вместо
слепого повторного запуска. На время восстановления новые conflicting действия блокируются.

Согласование изменения, допуск Apply и операции над Git учитывают конкретные hashes и HEAD.
Условия проверяются под lock при принятии команды и непосредственно перед эффектом. Изменение
исходных файлов извне требует повторной проверки и может вернуть работу на review. Лок на поток
сам по себе не блокирует внешний редактор или git-команду.

Для Git completion означает подтвержденный результат commit, а не только обновленную проекцию.
Если commit не удался, сохраняем понятный неуспех/ожидание, а не удаляем уже записанные факты.
После сбоя сверяем effect id и Git-результат, прежде чем повторять действие.

## Исполняемые спецификации

Сохраняем компактный YAML DSL и существующие stable ids. Замена синтаксиса не является этапом
этого плана. Новая коллекция технических проверок не возникает.

Для каждого переносимого процесса:

1. Сохраняем смысл и публичные expectations существующих контрактов.
2. Given prior events подаются через production decoder и projection path в disposable fixture.
   Clock, transport replies и версии внешних файлов остаются явно указанной средой. Нельзя
   записать готовый read model и назвать его историей событий.
3. When выполняет одну публичную операцию. В асинхронном процессе completion приходит отдельной
   публичной командой от transport adapter; runner ожидает только заявленную границу наблюдения.
4. Then сравнивает точный список новых событий выбранной границы, ответ и последующие GET.
   Адаптер не выдумывает события из ожидаемого состояния и не скрывает дополнительные проверки.
5. Читаемый отчет строится из исполняемого сценария: история, действие, последствия, конкретные
   расхождения. Документация генерируется из того же источника.

Прогон сохраняет исходные факты, команду, ответ, новые события и результаты сравнений один раз.
Построение отчета читает этот результат и не повторяет Given/When или setup. Cleanup fixture
выполняется и при ошибках подготовки либо команды. Это требования к реализации runner;
отдельные технические контракты или тесты для них без запроса владельца не добавляются.

Сегодня `then.events` означает только approval events. Это часть действующего договора.
Для расширения до всех domain events выбираем явную версию runner/контракта или scope
наблюдения и согласуем изменение смысла. Нельзя молча заменить `events: []`
в утвержденных сценариях на новые события или игнорировать лишние события ради зеленого corpus.
При изменении meaning/hash новый вариант проходит обычное owner review; старое согласование
не переносится на измененную семантику.

Новые contracts вводим только для важных для владельца правил, например восстановления его
решений, отсутствия повторного запуска работы после restart и работы native change без OpenSpec.
Одна ветвь parser или helper не становится самостоятельным контрактом.

## Этапы и критерии выхода

| Этап | Объем | Проверяемый результат | Зависимость |
| --- | --- | --- | --- |
| S0. Модель и исходная точка | Карта событий, gates и эффектов; короткий Event Storming с владельцем; фиксация текущего поведения и legacy boundaries. | У каждой операции известны команда, источник фактов, события, view и внешний эффект; спорные правила вынесены отдельно. | Исследование текущего change. |
| S1. Согласования | Command handler, replay state и storage boundary для approve/revoke/request changes/reattach/record approval; единый формат журнала и сериализация. | Существующие review contracts проходят без изменения смысла; события решает команда. Потеря только approval projection не теряет согласования. | S0. |
| S2. Обсуждения и решения | Перенос thread/message/patch/decision transitions в review scope; привязка завершения решения к Git-результату. | Полный review scope восстанавливается; blocking decision не считается выполненным до записи; replay не выполняет effects. | S1 и review новой event observation boundary. |
| S3. Инициативы и research | План, inputs, зависимости, owner decisions, разрешения чтения; отдельный cutover без автоматического импорта. Lifecycle общего execution остается в YAML до S4. | Согласование плана и исследовательские разрешения восстановимы из истории, drafts не становятся принятыми inputs. | S2; отдельное согласование изменения политики persistence. |
| S4. Исполнение | Устойчивые intents/results для reviewer, research, planner, author, Apply и verification; resume/stop/recovery. | Restart не дает самовольного повторного исполнения; реальный outcome и owner gate сохранены, неопределенный outcome виден явно. | S2-S3. Effect handling для уже перенесенного workflow делается в его срезе, а не откладывается целиком сюда. |
| S5. Проекции и отчеты | Rebuild, journal-based views и читаемый отчет; убрать авторитетные snapshots перенесенных областей. | Удаление только производных views восстанавливает те же публичные ответы без новых owner events и внешних действий. | S1-S4. |
| S6. Собственный пакет изменений | Общее представление change package; native Desk layout, stable-id corpus/results, независимое vetting и author/apply prompts. | Новый change проходит создание, review, исполнение и проверку без установки OpenSpec. Старый проект продолжает работать через adapter. | S5. Интерфейс пакета можно начать выделять раньше без смены поведения. |
| S7. Переключение Desk | Self-review использует native packages; удалить обязательный title join и CLI validation из native path. | Основной процесс Desk не требует OpenSpec; история и старые ссылки доступны; legacy/import/export остаются явной опцией. | S6 и сравнение результатов обоих путей. |

S1 начат с approve/revoke scenario и завершен переносом остальных approval operations в
[approval-command-events](../approval-command-events/design.md). Следующий бизнес-срез - S2. Инфраструктура растет ровно
на потребности этих срезов. Полный generic framework заранее не строим.

## Собственный пакет Desk

Рабочий вариант структуры, уточняемый в S6:

```text
features/*.desk.yaml                    # реализованный продуктовый corpus
desk/changes/<name>/change.yaml         # версия пакета, identity, ссылки на contracts
desk/changes/<name>/features/*.desk.yaml # предлагаемые contracts
desk/changes/<name>/proposal.md         # необязательное объяснение и rationale
desk/changes/<name>/review.events.jsonl  # история review
desk/initiatives/<name>/...             # инициативы и их история
```

Runtime logs и caches остаются в `.spec-review/`. Новую tracked структуру не размещаем в
gitignored runtime directory. Markdown остается удобным форматом пояснений; поведение
определяется исполняемыми контрактами. Генерируемая документация не получает независимую
редактируемую копию expectations.

Stable-id mapping нужен для approval keys, corpus comparison, verification results и ссылок UI.
Изменение места пакета не должно менять `features/<relative-file>::<scenario-id>`. Старые
title-based results разрешаются адаптером; неоднозначность требует явного исправления.
Импорт сохраняет hashes, history и происхождение, не создает approvals. Каталоги фраз Gherkin
и внешние OpenSpec проекты обслуживаются legacy adapter, пока они нужны пользователю.

Вынос OpenSpec за интерфейс включает discovery, room assembly, author output validation,
installation, Apply prompts, archive/import, конфигурацию и self-review scripts. Проверяем
полный native workflow при отсутствующем OpenSpec binary; одного переименования папки мало.

## Переход, откат и приемка

Каждый этап выпускается отдельным change. До переноса выбираем одного writer для области.
Новый read/replay path можно запустить параллельно только для сравнения без записи. Расхождения
публичных views, hashes и event sequence разбираем до переключения. Два независимых writers
YAML и событий не поддерживаем.

Перед переключением сохраняем исходные файлы и идентифицируем cutover version. Откат к reader,
не понимающему текущий формат, не поддерживается. Compatibility export не реализуется.
Неизвестные workspaces не изменяются; отказ чтения старого формата требует отдельного
решения владельца о данных, а не самостоятельного импорта агентом.

На каждом реализованном срезе запускаем `npm test`, `npm run typecheck`, соответствующие
существующие browser workflows и `npm run test:self`, когда меняются corpus/runner/self-review.
Ручная проверка использует disposable workspace и включает restart/rebuild именно перенесенной
области, сохранность старых hashes и отсутствие повторных effects. Она не превращается в
параллельный smoke/assertion suite. Технические unit/integration tests добавляются только по
отдельному прямому запросу владельца.

Оценку срока для S2-S7 уточняем после S1: пока не измерены объем legacy state, число активных
инициатив и последствия cutover для существующих worktrees. Этап готов по критерию поведения,
а не по проценту переименованных модулей.
