# Product onboarding

An existing product can span several independent repositories and supporting directories.
Declare its components in the selected workspace configuration and show an explicit product
overview even when no component has Desk changes yet. Missing components remain visible.

This first stage observes source availability, branch/revision, local changes, executable rule
count and runner configuration. Configuration is not proof of successful verification or owner
approval. Multi-repository execution and its source manifest are a subsequent stage.

Local Desk instances use port-specific session cookies so opening Monitoring on 4601
does not replace the self-review session on 4600. Authentication remains required.

The Monitoring pilot uses its six repositories and load generation directory. Android and other
Protok applications are outside that product. No application architecture migration is required.

Next: inspect one cross-component process, distinguish observed behavior from intended rules,
have a developer confirm public entry points and real observations, then draft compact owner
contracts. AI can prepare rules and adapters; the owner decides business meaning.
